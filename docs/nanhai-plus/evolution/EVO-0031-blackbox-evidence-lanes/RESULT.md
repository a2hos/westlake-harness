# EVO31 — 黑盒资格与静态扫描的证据解耦

**闭合：`PILOT_ONLY; NO_FLOW_CHANGE`。** 这次在 G299 raw、G300 NordVPN 资格、G300 Surfshark 资格及 G279 v13 R0 只读探针四组实际结果后反思一次；不延长到下一组，不改变 S1 主线或 canonical 计数。方向不同于 EVO30 的 manifest 根目录契约。

问题：200 APK 目标要求至少 100 个海外主流黑盒。G299 两个官方原版 ARM64 APK 的 raw 从 83 到 85，但资格、完整静态、冷启动均未增加；G300 独立资格把黑盒从 5 到 7，完整静态与冷启动仍各增加 0。两个包的发布者与 APK 签名证书绑定仍未独立证明。这些数字是**观察**，不是扫描受资格阻塞的证据。R0 也只读通过而不授权构图，进一步说明跨门槛误计是现实的控制风险，但不能把它当 APK 扫描吞吐的因果证据。

应保留的边界：G299 的“官方取件/raw 身份”不能当黑盒资格；G300 的五项资格不能当四阶段静态通过；静态通过不能当 OH7/Bionic 冷启动。现有 G299/G300 收据已经正确分开这些计数，没有观察到实际误计。**没有足够证据废弃现有动作或断言已有串行等待造成浪费。** 发布者签名绑定是待补证据，不能用 HTTPS 下载、APK 内证书 DN 或 Play 同包名替代。

唯一小试候选（假设，不推广）：下一组两枚新官方原版 APK 在 raw 独立接收后，给每个包建立一个 **`(APK SHA-256, scanner 代码 SHA-256, 四阶段规则/工具链 SHA-256)`** 的只读扫描键。四阶段 host 静态扫描可以从 raw 收据分支启动，同时资格核验在另一分支进行；二者各自出原始流、前后 APK SHA 守卫、独立审查和 root 准入。只有两条分支都引用同一 APK SHA，才可联合显示“qualified + static”，但资格与静态原有计数仍分别按各自 root 收据增加。APK、scanner 或规则/工具链任何一项变化使缓存键失效；缺任一阶段、原始流、前后 SHA 或独审时，扫描分支 NO_GO，不能填入完整静态。冷启动仍需独立设备证据。

机制假设：如果资格核验实测处在静态扫描的关键路径，这个内容键允许复用同一原版字节并平行推进两个互不依赖的 host 证据链，从而消除等待资格结果才开始扫描的空档。若下一组看不到此等待，或者并行扫描导致 SHA/工具链漂移、重复计算或误计，就判小试无收益并停止，不改现有 flow。记录 raw 接收、资格完成、四阶段扫描开始/完成、独审和 root 准入时间及每包实际 CPU/墙钟；与上一组在相同扫描器下的时序作比较。期望可验证结果仅为证据链一致且扫描启动早于资格结束、无误计，不能据此宣称 APK 启动提速。

适用：OH7.0.0.39/AOSP16 r4/ARM64 Bionic 目标的未修改 Android 黑盒原版 APK，host 静态扫描不接触设备或容器。反例：扫描器依赖资格才允许访问的密钥/许可证，或 qualification 会改变被扫描字节；此时两分支不能并行。当前两包已经完成资格，不能用它们伪造并行收益。下一轮只有 root 明确安排新两包试点后才执行；本次未创建扫描任务、未改 canonical、未发远端或设备命令。

过程数据见 `OBSERVATIONS.json`；本轮仅一个候选改进，状态待小试验证。
