# EVO62 — runtime scanner evidence gate (bounded reflection)

Four actual result groups were reviewed: HelloWorld H1–H4 is a 15-case **offline fixture** pass with zero remote calls; next4d's four APKs have root-limited exact raw and host-static admission with zero cold starts; 135 accepted static APKs are inventory-ready but runtime resolution is blind; TeamViewer QuickSupport gained root-limited raw/static/blackbox-input admission, still zero cold starts. These are different evidence levels. In particular, the H1–H4 synthetic positive is not a host identity, and a package's `DT_NEEDED` or JNI name is exposure, not a missing-provider runtime failure.

**One proposed change:** before dispatching `scan`/`benchmark` in runtime-resolution mode, require a same-build, ARM64 runtime index with ordered BCP JAR SHA values, bridge ELF SHA values, system ELF SHA values, exact R4 provenance, ABI and `runtime_lock_id`. If any component is absent, keep APK-local ZIP/manifest/DEX/ELF inventory available but label provider/member resolution `BLIND`, and do not launch runtime scan. This is a dispatch evidence gate, distinct from EVO61's cold-start APK ordering.

The offline `pilot.py` hashes the four frozen input receipts before evaluating the gate. Three rc 0 cases demonstrate the intended split: current evidence → `BLOCK_NO_TARGET_RUNTIME_INDEX`; synthetic complete contract → `CONTRACT_READY_NOT_RUNTIME_PROVEN`; historical empty-system-ELF index → `BLOCK_INCOMPLETE_SYSTEM_ELF_SHA256`. The synthetic case proves only schema behavior, not existence of a real target runtime. `TEST-RESULTS.json` records exact argv/rc/output hashes. Zero scanner, device, container or Bridge commands ran. Promotion requires an independently verified same-build index and one frozen-APK scanner pilot; only then consider a 135-way benchmark. No canonical scanner or queue was changed.
