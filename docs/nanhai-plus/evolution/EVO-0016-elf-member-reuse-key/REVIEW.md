# EVO-0016: exact ELF-member reuse key (local candidate)

Problem: APK static scans still redo completed ELF work after a package-level retry. Repeated cost: batch12-v2's Seal scan stopped on a ZIP payload named `.so`, while Briar exceeded its 90-second whole-package watchdog; batch12-v3 recovered by running 14 genuine ELF members separately. Decision: whether a completed member result can be reused safely on the next static-scanner attempt. Constraints: exact original APK bytes and scanner/tool pins, read-only trial, no device or global promotion. Completion evidence: a deterministic key over each accepted member receipt plus independent invalidation controls.

Primary lens: `_rethink_other_path`, different from EVO-0015's missing Soong owner probe. The current route rescans every member whenever a package is retried. Path A is the existing per-package scan; simple but loses completed work. Path B is per-member reuse only when a complete content key matches; it retains per-member receipts and still requires fresh whole-package manifest/DEX/aggregate/raw guards. The cheapest falsifier is key collision or failure to invalidate on a changed member, label, ABI, scanner, readelf, venv, or environment. We tested B's identity mechanism only, not actual cache use.

Observed anchors: `harness-stock-inventory-batch12-v3-candidate/HANDOFF.md` records Seal rc2 at `elf_header:lib/arm64-v8a/libaria2c.zip.so`, Briar rc-9 after 90.007 seconds, and the v3 recovery of six Seal plus eight Briar real ELF records with three ZIP-in-SO payloads typed separately. `harness-stock-inventory-batch12-v3-candidate/root-review-v1/ROOT-ACCEPTANCE.json` accepts only two complete static rows and no runtime result. G273 `stock-bionic-target-graph-v17b/root-release-v1/G273-REVIEW.json` remains graph rc2; A4 raw/root and A4 static v2 are separate intake/inventory evidence, and do not imply startup. Thus this trial only addresses scanner retries, not the Soong wall or 200 APK launch goal.

Discarded historical action: rerun a full Seal/Briar package scanner after one native-member failure. Observed failure and cause are the suffix-as-ELF assumption plus a non-resumable package timeout. Replacement: classify actual content, retain the already verified per-member receipt, and re-run only invalid members before a fresh aggregate. The v3 repair already implemented classification and member isolation; this evolution candidate adds the missing exact reuse key rather than repeating those changes.

Technical candidate: SHA-256 of a versioned ordered tuple `(member content SHA, archive member name, ABI, scanner.py SHA, readelf binary SHA, installed venv manifest SHA, environment SHA)`. `probe.py` applied it to all 14 accepted v3 ELF receipts. `TRIAL.json` records 14/14 matching member hashes and successful source/tool pins; 11/11 controls pass, including seven independent invalidation mutations and distinct observed keys. The stable-key control models a changed *outer* archive label with identical member bytes/name; it does not copy or rescan an APK. Trial rc0; runtime reuse performed: false; device commands: zero. The key must be invalidated if the command contract, transitive parser dependency, environment receipt, or tool identity differs. A prior accepted result cannot bypass raw APK identity checks or fresh aggregate completeness.

Causal chain: observed whole-package retry and timeout -> no member-addressed reuse identity -> exact versioned member/tool/source/environment key -> potentially omit unchanged `read_elf` calls on a repeated scan -> verify a subsequent isolated retry with cache hit/miss receipts and byte-identical ELF records. The 14 existing records show key feasibility, not a measured saved scan; no 89-tool or APK-startup delta is claimed.

Recommendation: keep as an unpromoted local candidate. Next evidence is one isolated scanner retry over the same accepted raw APKs with a cache reader that checks each source receipt SHA and produces hit/miss receipts, followed by independent byte-for-byte comparison against the original 14 records. Stop if any key field or receipt hash differs, a transitive dependency is unpinned, or a member is ZIP/unknown. Current-conversation user authorization covers recording evolution candidates; promotion into the shared scanner requires a separate owner review and root admission.
