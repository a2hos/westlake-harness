# 南海 plus：Bionic 主线 Goal

状态：用户已确认的当前架构目标。原生 goal 的同步状态以 OUTER-STATE 和原 owner 回读收据为准；文档启用不等于运行验收。

## 可直接使用的 Goal 正文

在 **OpenHarmony 7.0.0.39、android-16.0.0_r4、ARM64** 上，研发南海 plus 的 **App 进程单一 Bionic 架构**，使未修改的 Android APK 通过完整的 AOSP Framework/ART 和操作系统边界适配，使用 OpenHarmony 系统服务运行。近期交付以 HelloWorld 的安装、冷启动、真实上屏、输入交互、生命周期和正常退出闭环为中心，同时完成原 89 项工具的架构归属审计及适用工具的构建、真实消费者验证。随后继续原项目的 10 APK 核心版、30 APK 扩展版和 AIDL/API 契约目标。

以 adapterBio3 为架构参考，显式处理其 AOSP14/ARM32 与本目标的差异；只读参考 BridgeAOSPV16 的同方向设计、实现与失败证据，在本项目独立工作树中并行研发。参考项目尚未上屏，其声明、构建和局部成功均不能代替本项目验收。

本目标直接推进 Bionic。既有 Musl 工作保留为历史证据、对比输入和适用源码/测试经验；Musl 首屏、整批工具或 APK 完成不再是 Bionic 开始工作的依赖。

## 架构契约

1. **单一 Bionic 的边界是 Android App 运行进程。** 其 linker、libc、pthread/TLS、ART、JNI、native 依赖，以及装入该进程的 OH client 库，必须属于已核定的 Bionic ABI 组合。OH 系统服务可继续运行在自己的 Musl 进程，通过明确的 IPC、FD、共享缓冲区和回调协议连接。
2. OH client 源码需要在 App 内运行时，按目标 Bionic 工具链、头文件、C++ ABI、构建参数重建。禁止把 OH 原生 Musl DSO 装进 App，再用符号转发、TLS 切换或 pthread 兼容壳把混合进程报成单 Bionic。IPC/FD 之外的跨进程共享对象须有明确线格式、所有权和生命周期；不跨 libc 传递 pthread、C++ 对象或分配器所有权。
3. 启动链要证明 OH 侧创建/安全管控与 Bionic 进程初始化的完整交接，核定 zygote/appspawn 的具体角色。仅从 Musl 父进程 fork、仅生成一个叫 `libbionic` 的库、仅修改 ELF 解释器路径，均不足以证明架构达成。
4. AOSP Framework、ART、BCP 的 Android 语义保持完整。适配落在服务路由、JNI/native bridge 和 OS 边界；禁止用 class linker、vtable、entrypoint 或业务方法补丁掩盖边界缺失。真实原生能力优先采用对应 AOSP 源实现；占位实现单列。
5. 不新增整套 Android `system_server` 作为兼容后端。AMS/PMS/WMS 及其他调用按 AOSP16 契约映射到 OH provider/bridge，保留调用者身份、权限、错误、回调、生命周期和恢复语义。
6. 图形与输入需要真实的窗口、Surface/BufferQueue/RS 所有权、buffer 提交/释放和输入回传链。`onCreate`、离屏绘制、空白窗口或截图单证不等于上屏交互闭环。
7. AOSP14→16、ARM32→ARM64 均按精确源码和接口核差异。不得沿用旧 boot/oat/ELF/JAR、汇编偏移、寄存器假设、结构布局或版本不明的设备脚本。ART、dex2oat、BCP、boot image 必须有同代来源与配置证据。
8. APK 业务保持透明。诊断版 HelloWorld89 可按用户要求加入小功能和观测点；每次冻结 APK SHA 和测试清单。其通过只证明覆盖的能力，通用兼容性还要由未修改基准 APK 验证。
9. 安全策略不得静默降级。权限、签名、SELinux、AccessToken、调用者身份及 UID/GID 必须有真实正负场景；旧参考中的放宽安全命令不作为本项目默认启动步骤。
10. **整个项目杜绝容器。** 构建、扫描、测试、桥接及 App 运行均不用 Docker/Podman/OCI 镜像或容器内进程，也不用 nsjail、unshare、chroot 或同类 OS namespace 隔离作为替代。精确 AOSP16 R4 源码在原生宿主上只读消费，构建产物落本项目独立 OUT/TMP/staging。历史容器收据只解释当时失败，不计为原生宿主构建通过；G277/v21 容器候选已撤销，不得封包或重放。

## 版本和产物准入

| 范围 | 固定要求 | 首次执行前应补齐的事实 |
|---|---|---|
| AOSP | `android-16.0.0_r4`，ARM64 | 所需仓库 manifest/commit、补丁、release config、实际编译器及 sysroot；目录名不证明完整源码 |
| OH | `7.0.0.39`，SDK 编号 `26.0.0.39` 分列 | manifest、产品/板型、所用 provider 源码与设备镜像身份；同 `.39` 标签不等于同构建 |
| App 运行时 | Bionic | ELF/解释器、完整依赖来源、实际映射与动态加载、线程/TLS 和边界调用验证 |
| OH 服务侧 | 与目标设备匹配的 OH 系统域 | OH 原生产物只在其适用服务/系统域使用；不作为 App 内 Bionic 库直接复用 |
| 输出 | 本项目独立构建代 | source、patchset、toolchain、argv、输入闭包、输出 SHA、安装路径、设备/boot 身份 |

工具链按各自构建域绑定。GZ02/alexpc 已核对的 OH Clang 15.0.4 `02fbe8` 是 OH 构建事实；不能据此替代 AOSP r4/Bionic 的工具链和 sysroot 选择。共享源码仍从 `NANHAI_SOURCE_POOL_ROOT` 只读消费，工作树、输出、临时目录和运行目录独立。

## 里程碑与退出条件

里程碑描述依赖关系，不要求全项目串行。独立工具、契约、图形/Input 预研可并行；设备集成逐个关闭当前最早失败点。

| 里程碑 | 交付 | 通过所需证据 |
|---|---|---|
| B0 架构与输入绑定 | 进程/库归属图、版本锁、89 项处置表、首条可执行依赖链 | 精确来源、缺项与写集明确；逐包检查实际依赖，不以全部环境齐备阻塞已就绪包 |
| B1 Bionic 基座 | ARM64 linker/libc/线程/TLS 与所需 client 构建链 | 构建、加载依赖及小型进程运行证据；纯原生探针通过单列，不替代 App 证明 |
| B2 安装与进程启动 | 包身份、UID/GID/权限、OH 创建过程及 Bionic 交接 | 正负安装场景、真实子进程身份和加载图；安装与运行基座工作可并行准备 |
| B3 Java 生命周期 | 同代 ART/BCP/boot，Framework 进入真实 Activity 生命周期 | 冷启动进程、hilog/trace、回调顺序；无语义替换/伪成功 |
| B4 首帧与输入 | HelloWorld 自身窗口内容上屏、按钮/触摸改变可观察状态 | 同代截图、present/buffer 证据、输入到应用回调及状态变化；再次冷启动复现 |
| B5 HelloWorld 闭环与工具验证 | 正常退出/重启、权限负例、诊断功能；适用工具真实消费者 | 安装→冷启动→首屏→交互→退出/恢复完整链；每项工具按归属验证 |
| B6 核心版 | 未修改的 10 APK 与 AMS/PMS/WMS 核心契约 | 各 APK 完整闭环；服务的正常、负向/权限、生命周期和恢复场景独审 |
| B7 扩展目标 | 原 30 APK、AOSP16 AIDL 逐方法清单及原系统 API 范围 | 范围有账可查、实现/验证/缺失分别列出；性能按实际测量和既定阈值另验 |

冷启动必须排除旧进程、旧运行时代、旧缓存和热启动影响；需重启或部署时遵守当时设备操作授权与恢复检查。本修订不复制参考项目的设备授权。先完成一次完整可诊断链，再要求同条件复现；重试必须绑定改变了的输入或待验证假设。

## 89 项工具的处理与计数

原 89 条工具 ID 保留，不删行、不改变分母来制造完成率。每条增加新目标 `oh7.0.0.39-aosp16r4-arm64-bionic` 的独立记录，填写：架构归属、真实消费者、保留/重建/替代决定、输入来源、验收方式、状态和证据。

| 归属 | 处理 | 验收方式 |
|---|---|---|
| 宿主构建/生成工具 | 精确版本与输出语义可复用时核验复用，否则重建 | 真正执行工具并检查生成物及下游消费；不造 APK 按钮当宿主工具测试 |
| App 内运行库 | 目标 ARM64/Bionic 重建并核对传递依赖 | 同 Bionic 进程内的真实调用、错误/边界场景与加载来源 |
| OH 服务侧组件 | 只在其声明的 OH 系统域绑定 | 通过实际 IPC 消费者验证服务行为和权限；不混入 App ELF 集合 |
| 数据、JAR、APK 与资源 | 按 ABI/版本/配置影响审计，满足契约才复用 | 生成/解析及真实运行时消费；转换、复制不等于源码重建 |
| 旧 Musl 兼容层或被原生能力替代项 | 记录退休/替代原因、能力去向和替代验证 | 单列 `retired_by_architecture`；不记为工具测试 PASS，不为凑 89 个库恢复双 libc |

历史 `58/89 已尝试、38/89 源码接受、12 项限定原生、0/89 整项接受` 留在 Musl 目标。Bionic 的通过数只随新目标证据增加，不能按名称继承。尤其 G227 的 `libwestlake_bionic.so` 是 Musl 目标下的兼容库重建记录，不代表完整 Bionic libc/进程架构已实现。

分别报告：89 项已处置数、适用工具验证 `A/A_total`、退休/替代数、失败/未验证数，以及 B0–B7、HelloWorld 和 10/30 APK。处置完 89 项不等于 89 项测试通过；HelloWorld 上屏不等于整个 goal 完成。

## 并行与终态

外环统一调度；基座/依赖、服务与安装、图形/Input 与 APK 测试可按不相交写集并行。BridgeAOSPV16 是可读取的参考源，不是本项目开始或通过的前置条件。集成由单一 owner 合入精确版本并验收。

专职反思 peer 继续约每 3–4 组已独审实际结果做一次不超过 120 秒的复盘，最多提出一个可验证改进；方向由本轮证据决定，不固定轮换。输入准备、方案审查和本次文档修订不计实际结果组，不阻塞其他工作。

仅当规定范围的能力、适用工具、APK 和契约都有证据，架构不变量与未决失败完成审查，才可宣布相应阶段完成。不得以 host build、静态检查、参考项目成绩或看板计数代替本项目真实运行。
