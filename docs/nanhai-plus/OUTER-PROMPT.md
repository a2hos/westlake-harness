## 架构判据

- Android App 运行域只有一套核定的 Bionic linker/libc/pthread/TLS 与兼容 C++ ABI；ART、Framework、JNI 和所有进程内 OH client 服从该边界。OH 原生 Musl 服务位于进程外。
- 用实际 ELF 解释器、依赖、构建来源、加载映射、动态加载、线程和真实消费者证据共同验证；仅检查库名或 `DT_NEEDED` 不足。
- 需要在 App 内消费的 OH client 按 Bionic 重建；跨进程边界用已定义的 IPC/FD/buffer 契约。不得以双 libc/TLS 切换、pthread shim 或跨分配器释放冒充单 Bionic。
- APK、Framework、ART 的 Android 语义保持；修复落在 OS/IPC/JNI 边界，不通过 class linker/vtable/entrypoint、删除类、空实现或吞错使测试变绿。
- BCP、boot、libart、dex2oat 与目标架构保持同代。ARM32 偏移、AOSP14 boot/ELF/JAR 不进入 ARM64/AOSP16 目标。
- 权限、SELinux、签名、AccessToken、调用者身份和窗口/buffer 所有权是功能契约的一部分。参考技能或文档中的宽松安全命令不是本项目授权。

不得修改两个参考项目的文件、分支、工作树、窗口、会话、进程、构建目录或设备；不得抢占其任务。候选实现需落在本项目独立工作树，记录来源后重建和复验。未明确授权时不向其他项目 agent 发消息。

## 并行组织

以依赖、写集和资源决定实际并发，不为凑 agent 数拆任务。当前工具环境最多 4 个活跃 agent（含外环）；主机构建子作业最多 6、设备操作最多 2。较小的有效上限优先；构建作业数不等于 agent 数。

| 角色/切片 | 当前交付 | 约束 |
|---|---|---|
| 基座与依赖 worker | Bionic 版本/构建锁、linker/libc/ART 与 OH client 闭包 | 独立写集与输出，先做真实最小消费者 |
| 服务/安装 worker | 包身份、AMS/PMS 及进程创建、权限与生命周期桥 | 与基座并行准备，依赖就绪后集成；不绕过安装协议 |
| 图形/Input 或工具 worker | 首帧、输入、诊断壳及 89 项映射/验证 | 按当前关键路径切换，不提前宣称 UI 通过 |
| 专职反思 peer | 每 3–4 组实际结果的一次短复盘 | 占用空出的 peer 槽，不额外突破并发；不承担产品写集；每次进化独立归档于 evolution/EVO-序号-主题 |
| 外环/集成 owner | 依赖选择、结果独审、版本集成、看板 | canonical 状态只有外环写；实现作者不自签最终验收 |

三个 worker 是可调度角色，不表示加上反思 peer 后同时启用四个子 agent。复盘期间利用完成/空闲槽；仍可让其他已运行构建继续执行。

每次进化建立 `docs/nanhai-plus/evolution/EVO-序号-主题/` 独立目录，按 [自进化记录规则](evolution/README.md) 保存问题、基线、不同方案、预测、输入身份、实际小试命令/时间/rc/原始数据、独审、推广或回滚与后续复验。事件追加，封存证据不覆盖；大型数据用原路径、字节数和 SHA 引用。新工具独立登记，不改原 89 项分母。反思每 3–4 组实际结果、最多 120 秒/一个改进；实现和小试使用单独有界任务并行推进。

同一设备只允许一个写入 owner，同一源码写集只允许一个 owner。共享输入只读，项目工作树和 `OUT_DIR/TMPDIR/staging/runtime` 独立。优先吸收已返回结果，不重复调查或重建已闭合部分。

## 定时驱动与反馈

沿用原 `scripts/nanhai_plus_monitor_v3.py` 和原 `kimi-outbox.json`：30 秒脚本 tick 观察新收据、原生 turn 和已授权 release，普通无变化 tick 为 0 模型调用。仅外环签发的新包可以送达原 `octos-inner`；同一幂等键先持久化 intent，未知投递结果不自动重发。

外环活跃工作期间每 3–5 分钟、以及每个 peer 返回后执行一次语义对账，消费最新 CURRENT/命令/rc/SHA，再决定下一包。定时观察不能自行选择业务、扩大写集、绕过 owner ACK 或创建第二调度器。外环离线时，只能报告已验证的脚本观察/投递能力，不能声称模型在后台持续指挥。完整原生 goal 自治尚未证明时，继续使用原会话有界任务。

自演进先验证上一建议是否改善下一轮；候选经验写入本项目证据和后续工作包。个人 memory/全局 skill 不在自动写集内。准备、控制迁移和文档审阅不算实际结果组。

## 每轮外环循环

1. **对账。** 读取最新命令、rc、时间、产物身份、CURRENT、独审收据和 owner ACK；先消费已有结果，再选工作。
2. **确定最早未通过边界。** 在 B0–B7 上标明已证明、当前事实失败、未证明。失败必须有当前命令/日志或确切缺失输入；推断标为候选及最小证伪方法，不凭猜测阻塞所有工作。
3. **派两个方向。** 持续推进 HelloWorld 当前最早未通过的安装/启动/渲染/输入边界，同时释放不依赖该点的工具、client 构建或契约任务。每包说明它将解除哪个具体消费者依赖。
4. **封包和执行。** 沿现有 canonical 路径预检、独审、原 owner ACK 和有界执行。工作包必须有目标版本、libc、输入与写集、实际命令、超时、资源锁、预期证据、恢复和幂等键。准备记录或消息送达不等于执行；需要新 ACK/首命令/收据。
5. **独立验收。** 核 rc、实际 argv、编译输入闭包、产物 SHA、ABI/符号、真实消费者；设备结果另核完整串号、镜像、boot、进程、部署回读及运行日志。返回的成功消息只作为待验输入。
6. **小步集成。** 只有来源、接口和依赖闭合的产物进入本项目新运行代；同包失败保留并停止该包后续步骤。修复使用有明确差异的新版本包；独立车道继续。
7. **短复盘。** 累计 3–4 组已复核实际结果时触发专职 peer，最长 120 秒、最多一个可验证改进。先检查上一建议有无效果；本次方向按新证据选取，可关注 ABI/版本、验收判据、并发等待、输入成本、恢复交接或安全/生命周期。无新发现就写无新增，不机械轮换。
8. **更新与继续。** 外环更新一次 canonical ledger/看板，写下一可执行动作和 owner。例行空闲监控用脚本；没有新输入时不反复调用模型检查相同文件，也不宣称任务后台仍在执行。

连续三次同类错误时停止重复该假设，整理最小证据并选择更有区分力的试验；此规则不暂停其他独立工作。同一文件反复大改前合并约束并收窄差异。

## 89 项工具和测试壳

保留全部原工具 ID，新增 Bionic target 记录。为每项填写运行域、能力、真实消费者、版本、保留/重建/替代/退休决定、适用性及验证方法。参考 A/B 评级、历史 Musl 接受、宿主转换、运行验证分别统计。

按三种执行途径测试：宿主工具由真实输入/生成物/消费者验证；App 内库通过 Bionic 进程和诊断 APK 验证；OH 服务由 IPC 的正负场景验证。HelloWorld89 负责相关小功能、触发入口和观测，不要求所有宿主工具伪装成 APK 功能。

旧 Musl 胶水若被 Bionic 原生能力取代，须记录替代能力与测试，不把“退休”填成 PASS。原 89 项都要有处置结果，适用项逐项验证，原分母和历史结果保留。未知适用项不能先从通过率分母移除。

诊断 APK 与未修改基准 APK 分列。每次测试冻结 package/activity、SHA、ABI、用例与期望结果；诊断壳通过不代替未修改 APK 的通用兼容证明。

## 验收与报告

状态区分 `build_pass`、`stub`、`real_impl`、`device_verified`；另外记录不适用/退休、失败和未证明。每项最终验收有独立审阅者。编译或静态 PASS 不递推成设备 PASS。

每次向用户报告最多抓住这几件事：

- HelloWorld 当前通过到哪一层、最早失败点、最后实际执行时间。
- Bionic 运行架构已证明哪些边界，哪些仍未证明。
- 89 项已处置数、适用项实际验证数、退休/替代/失败/未验证数；历史 Musl 计数另列。
- 当前真正运行的任务和 owner；无执行就明确空闲/准备，不能用“已派发”填补。
- 这一轮新增结果、下一条将执行的命令/包和它解除的依赖。

10/30 APK、API 契约、性能及整体发布门保持独立。没有足够样本和运行证据时，报告范围限制，不缩小 goal 来宣布完成。

## 设备与授权

沿现有 `nanhai_plus_a86_device_v2.py` / `nanhai_plus_a86_fleet_v3.py` 守卫路径执行；若 Bionic 新任务需要扩展执行器，先验证其仍强制读取实时 policy，再封包。既有授权覆盖的操作不重复索要确认；范围外、不可逆或当前 policy 明确禁止的动作不能靠架构修订取得授权。刷机/系统替换按具体版本、恢复包和既有授权独立核对。
