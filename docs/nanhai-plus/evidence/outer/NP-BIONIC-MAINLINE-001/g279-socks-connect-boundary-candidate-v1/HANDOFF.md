# G279 SOCKS CONNECT boundary handoff (code only)

Decision: **GO for an offline reply parser; NO_GO for treating a SOCKS5 REP=0 as evidence of node outbound TCP or gz02 reachability.** No live release is requested by this handoff.

The smallest possible connection point in the frozen v7 runner is inside `run_instance`, after `socks_negative(port)` has closed and `LOCAL_REJECT_WITNESS` has been recorded, and before the `ssh_probe(...)` call. The existing `recv_exact` and `complete_reply` functions already read a complete SOCKS5 reply, including IPv4, domain, and IPv6 BND address forms. A separately reviewed generation could open one loopback connection to the *same private listener*, exchange the no-auth greeting, send the fixed `socks_boundary.request_frame()` bytes for the pinned gz02 IP and port, call `complete_reply`, then classify its bytes with `socks_boundary.parse_connect_reply`. It must not call `ssh_probe`, `/usr/bin/nc`, or the v7 `ssh_argv` path. It must not modify or replay the consumed v7 runner/release/nonce.

That local client sends no proxy credential: the greeting is `05 01 00`. It does cause the private Mihomo instance to use its copied selected-node credential, so it is **a real outbound attempt** and needs a new exact root release and independent code review. To avoid enlarging credential exposure, a future implementation must retain v7's source/controller/selected-leaf pinning, private directory mode `0700`, config mode `0600`, selected-node alias, project-local OUT, private process cleanup, one-shot nonce, and no global proxy writes. It must not persist source config, selected leaf, raw private logs, BND address bytes, or the full reply. Only a bounded status/REP, reply length, SHA-256, and already-whitelisted local route line could leave the private boundary. Hashing the full reply is safe only after checking that the BND field cannot itself be sensitive under the project's evidence policy; otherwise omit that hash too.

**Critical limitation:** v7's `socks_negative` comment records that this exact Mihomo binary can return a complete `REP=0` before a `MATCH,REJECT` route closes the stream. Therefore `REP=0` is merely the proxy's local acceptance of CONNECT, not proof that the selected node established outbound TCP. A nonzero REP would refute local CONNECT acceptance in that one run, but would not identify the failing hop. The code-only oracle deliberately exports `remote_tcp_proven=false` and `gz02_identity_proven=false` for every REP. A subsequent timeout or EOF after REP=0 would still be ambiguous. Do not add this pilot to the current v7 success path as an outbound gate, and do not spend another live one-shot solely to obtain REP=0.

The next useful falsifiable evidence would have to observe a byte that originates beyond the proxy's local ACK, for example a bounded SSH identification banner on the same CONNECT stream. That would be a new network experiment to the target port, even if no SSH client, host key, or authentication is used; a banner alone is spoofable and cannot establish gz02 identity. Authenticated identity still requires a separately reviewed, pinned host-key/auth/UID path. If this extra experiment is not acceptable or cannot retain a privacy-safe byte-level witness, record `UNKNOWN` and seek a fresh authenticated native Linux host entry instead.

Current evidence: v7 root postrun acceptance SHA-256 `850edde1111318928555dbccb9b00e8939496ab128ee0e1d81a8ea3ceb05ef6b` and peer postrun SHA-256 as pinned in `CANDIDATE.json`; both accept only the local `/32 PROXY` rule line and bounded SSH failure. The offline parser fixtures pass 12 valid and 8 invalid cases. No proxy, SSH, target network, device, container, namespace, or BridgeAOSPV16 operation was run for this handoff.
